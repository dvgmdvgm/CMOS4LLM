# CLAUDE.md — инструкции для Claude в этом проекте

> Этот файл подгружается **автоматически** в начало каждой сессии в `D:\AI Projects\CMOS\`.
> Здесь не «шпаргалка», а **исполняемый протокол**. Если в этом файле написано «сделай X на первое сообщение» — это значит сделай, без переспроса.

---

## ⛔ HARD GATE — WAKE-UP RITUAL (выполняется на ПЕРВОЕ сообщение сессии)

**Перед любым ответом на первое содержательное сообщение пользователя в этом проекте:**

1. Прочитай `STATUS.md` — где мы сейчас (1 экран).
2. Прочитай `NEXT.md` — что делаем дальше (1 экран).
3. Прочитай **самый свежий** файл в `docs/09-conversation-log/` (по имени файла, формат `YYYY-MM-DD-*.md`).
4. Если в `NEXT.md` упомянут `ROADBLOCKS.md` или есть открытые блокеры — прочитай и его.
5. **Доложи пользователю одним абзацем:**
   - На каком этапе мы сейчас (фаза + % готовности).
   - Что было сделано в прошлой сессии (1-2 пункта).
   - Что следующий шаг по `NEXT.md`.
   - Есть ли блокеры, которые надо решить ДО реализации.
6. Жди подтверждения или коррекции от owner'а. После ОК — приступай.

**Это не опционально.** Это и есть wake-up resilience: owner может вернуться через дни/недели и за 30 секунд получить корректную картину.

### Триггер-фразы, после которых wake-up + сразу за работу

Если первое сообщение — одна из этих фраз (или близких по смыслу), выполни wake-up как описано выше, **затем сразу берись за первый незакрытый пункт из NEXT.md**, не дожидаясь дополнительной команды:

- «переходим к реализации»
- «продолжаем»
- «продолжай»
- «дальше»
- «next»
- «go»

В этом случае структура ответа: краткий wake-up отчёт (3-5 строк) → «Берусь за пункт N: …» → начинаешь работу.

### Когда первое сообщение — конкретная задача

Если первое сообщение содержит конкретную задачу (например: «обновить ADR-005» или «написать спеку Component X»):
1. Всё равно сделай wake-up (пункты 1-4 выше).
2. Сверь задачу с `NEXT.md`: если она в очереди — берёшь её. Если нет — мягко уточни у owner'а, не сбился ли scope.
3. После 1-предложения wake-up отчёта приступай.

## ⛔ HARD GATE — SLEEP RITUAL (выполняется при завершении задачи)

**Sleep-ритуал запускается в одном из случаев:**

- Закрыт значимый пункт из `NEXT.md` (не просто «прочитал файл», а «написан/обновлён артефакт»).
- Owner написал одну из фраз: «сохраняемся», «закрываем сессию», «конец», «end session», «save», «сохрани».
- Сессия достигла естественного завершения (большая задача целиком закрыта).

**Что делать:**

1. **Обнови `STATUS.md`:**
   - Поменяй «Дата последнего обновления».
   - В блок «Что сделано в последнюю сессию» — занеси конкретные артефакты (имена файлов, ключевые решения).
   - Обнови «Текущая фаза» и «% готовности».
   - Скорректируй «Где мы в roadmap» если нужно.
2. **Обнови `NEXT.md`:**
   - Удали пункты, которые закрылись в этой сессии.
   - Добавь новые пункты, если они появились в ходе работы.
   - Сохрани приоритетность (1 = ближайший).
3. **Создай новый файл** в `docs/09-conversation-log/YYYY-MM-DD-<topic>.md`:
   - Формат имени: дата-кебаб-тема (`2026-05-26-scope-and-automation.md`).
   - Содержание: контекст сессии, ключевые решения, **почему именно так**, ссылки на изменённые файлы и созданные ADR.
   - Это самый важный артефакт — он объясняет рассуждение, а не только результат.
4. **Если приняты архитектурные решения** → новый ADR в `docs/02-decisions/` (нумерация по порядку, формат шаблона `000-adr-template.md`).
5. **Если возникли открытые вопросы** → добавь в `ROADBLOCKS.md` с уникальным Q-номером.
6. **Доложи owner'у:** одним абзацем — что записано, в какие файлы, и что safe закрывать окно.

**Никогда не пропускай sleep-ритуал.** Если owner забыл — напомни сам. Один пропущенный sleep = одна испорченная следующая сессия.

### Что делать, когда задача не доделана, но сессия заканчивается

Это нормальный сценарий. Sleep-ритуал в этом случае:
1. В `STATUS.md` — пишем «в работе: <название>, <% готовности>».
2. В `NEXT.md` — переформулируй пункт как «продолжить <название> с точки <X>».
3. В conversation-log — обязательно зафиксируй, на каком шаге остановились, чтобы не пришлось разбираться заново.

## Wake-up resilience — главное правило этого проекта

Owner может уйти на дни/недели и вернуться. Любое окно чата должно восстанавливать контекст за 5 минут чтения README + STATUS + NEXT + последнего conversation-log.

Это означает:
- Sleep-ритуал — обязательный, не «по желанию».
- Никогда не делай архитектурных решений без записи rationale в ADR.
- Никогда не повышай scope из Future / V2 в MVP без явного согласования с owner'ом и без отметки в ROADMAP.

## Архитектурные принципы (нерушимые без ADR)

1. **CMOS — внешний слой**, не модификация LLM. Никогда не предлагай решения «давайте дообучим модель» без явного V3 контекста.
2. **Two-LLM economy:** тяжёлая когнитивная работа (extraction, summarization, dedup, drift detection) → локальный Sub-LM. Cloud LLM получает только сжатый, отфильтрованный, валидированный контекст. Не отправляй raw chat в cloud.
3. **Stateless LLM, stateful CMOS:** LLM — co-processor. Source of truth — CMOS. Все persistence — на стороне CMOS.
4. **Memory hierarchy L1–L5 строгая.** Не сваливай всё в один store. Каждый уровень имеет свои свойства (см. ADR-002).
5. **Multi-project из коробки** (ADR-004). Никогда не assume один проект.
6. **Time Travel Debugging — first-class в V1** (ADR-005). Это диктует event-sourced хранилище inferences. Не ломай этот контракт.
7. **Counterfactual mode — реализуем** (ADR-008). Архитектура должна позволять воспроизводить inference с изменёнными inputs.
8. **GUI плотность — высокая** (ADR-006). DevTools-style. Не «упрощай для удобства».

Любое отклонение от этих принципов требует нового ADR + явного согласования с owner'ом.

## Правила работы с кодом (когда дойдём до имплементации)

1. **Tests first для всех memory primitives** — иначе невозможно гарантировать корректность retention/promotion.
2. **Никаких комментариев-шума** — комментарий имеет право на жизнь только если объясняет неочевидное «почему».
3. **No silent fallbacks.** Если не получилось — кричи. CMOS не может «угадывать», когда речь идёт о памяти.
4. **Latency-budget на critical path:** retrieval planning + assembly < 200ms p95. Sub-LM работа на critical path — не более 1 вызова. Всё остальное — в background.
5. **Никогда не удаляй данные из L4/L5.** Только tombstone. Versioning сохраняет всё.

## Что точно НЕ делать

- Не лей фичи в MVP, которые не в `docs/03-scope/mvp.md`.
- Не используй RAG в наивном виде («top-K vector») как единственный retrieval механизм. Hybrid required.
- Не предлагай chat-history-as-memory (это и есть проблема, которую CMOS решает).
- Не делай blocking calls в cloud LLM для bookkeeping задач (extraction, summarization). Только Sub-LM.
- Не делай GUI «красивым» в ущерб плотности информации.

## Когда в сомнениях — спрашивай

Owner предпочитает обсуждать архитектурные решения, а не получать готовый код. Если развилка — сформулируй варианты и trade-offs, дай рекомендацию, попроси решение.

Имплементацию делаем **после** того, как scope/архитектура зафиксированы.

## Бенчмарк honesty

CMOS обещает 5–25× снижение токенов на типичных задачах. **Никогда не утверждай результат без измеренного baseline.** В Token Analytics симулируется alternative reality (без CMOS), и сравнение идёт против неё. Любая цифра в документации, маркетинге или discussions должна быть прослеживаема к воспроизводимому бенчмарку.

100× — возможно для best cases, не baseline. Не обещаем то, чего не сможем сдержать.

Если owner написал команду явно — это явный триггер, выполни немедленно:
